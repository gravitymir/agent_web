# Hardening backlog (для использования вне localhost)

Приложение спроектировано как **локальный инструмент** (по умолчанию `127.0.0.1:8787`, без аутентификации). Через него можно выполнять код (`Bash`) и читать/писать файлы в воркспейсе — поэтому **выставлять его в сеть/интернет в текущем виде нельзя**. Ниже — заметки на будущее: что усилить, прежде чем открывать доступ извне.

> Статус: **не реализовано**, backlog. Порядок — по приоритету.

---

## 1. Аутентификация обязательна перед сетевым биндингом (highest priority)

**Риск:** сейчас нет никакой аутентификации. Если задать `CWI_BIND=0.0.0.0:8787`, вся локальная сеть (или интернет при пробросе портов) получает **RCE** через инструмент `Bash` и полный доступ к файлам воркспейса.

**Сейчас:**
- Бинд-адрес: [`src/config.rs:38`](../src/config.rs) — `CWI_BIND`, дефолт `127.0.0.1:8787`.
- Слушатель: [`src/main.rs:169`](../src/main.rs) — `TcpListener::bind(&config.bind_addr)`.

**Что сделать (минимум):**
- В `src/main.rs` при старте — `tracing::warn!` (а лучше жирное предупреждение), если `bind_addr` НЕ loopback (`0.0.0.0`, `::`, или не `127.0.0.1`/`localhost`) и при этом аутентификация выключена.
- Полноценно: перед разрешением не-loopback биндинга **требовать** механизм аутентификации (токен/пароль в заголовке или cookie, middleware в Axum), иначе — отказ старта. Токен-миддлварь можно навесить рядом с `add_security_headers` (см. `src/main.rs`).

## 2. Защита от DNS-rebinding / SSRF в WebFetch

**Риск:** `is_blocked_host` проверяет только IP, **явно указанный в URL** (плюс `localhost`). Публичное имя, которое DNS резолвит в приватный/loopback IP (**DNS rebinding**), проходит проверку — агент может достучаться до внутренних сервисов (`169.254.169.254`, `127.0.0.1`, интранет).

**Сейчас:**
- [`src/agent/tools.rs:750`](../src/agent/tools.rs) — `fn is_blocked_host`. В комментарии на строках 748–749 ограничение уже честно отмечено.
- Проверка вызывается в WebFetch: [`src/agent/tools.rs:782`](../src/agent/tools.rs).

**Что сделать:**
- Принудительно резолвить хост **перед** запросом (`std::net::ToSocketAddrs` / `tokio::net::lookup_host`) и прогонять **каждый** полученный IP через те же `is_loopback() / is_private() / is_link_local() / is_unspecified()` (v4) и loopback/ULA (v6), что уже есть в `is_blocked_host`.
- Чтобы избежать TOCTOU (резолв → другой IP при коннекте): зафиксировать проверенный IP через `reqwest::ClientBuilder::resolve(host, addr)` и ходить именно на него. Тогда «проверили один IP, подключились к другому» невозможно.
- Не забыть про редиректы: каждый hop редиректа тоже надо проверять (или запретить редиректы и проверять вручную).

## 3. Явный таймаут на чтение потока Bash (надёжность, low priority)

**Наблюдение:** `read_capped` отлично лимитирует **размер** вывода, но сам по себе не ограничивает **время** чтения зависшего потока.

**Сейчас:** это уже **косвенно закрыто** — вся операция `run` (включая оба `read_capped` для stdout/stderr) обёрнута в `tokio::time::timeout(BASH_TIMEOUT, run)`:
- [`src/agent/tools.rs:57`](../src/agent/tools.rs) — `BASH_TIMEOUT = 120s`.
- [`src/agent/tools.rs:435`](../src/agent/tools.rs) — обёртка `timeout`.
- [`src/agent/tools.rs:464`](../src/agent/tools.rs) — `read_capped`.

**Что можно сделать (по желанию):** для гранулярности обернуть непосредственно чтение стрима в отдельный, более короткий `tokio::time::timeout`, чтобы «медленный, но не мёртвый» вывод отсекался раньше общего 120-секундного лимита. Приоритет низкий: текущая обёртка гарантирует, что процесс чтения не висит дольше `BASH_TIMEOUT`.
